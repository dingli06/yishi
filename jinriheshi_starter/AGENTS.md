# 今日何食：开发 Agent 工作约定

## 目标与当前范围

把 HowToCook 的可追溯正文转成能够持续维护的菜谱数据，并在此基础上开发微信小程序：少量输入 → 推荐一道菜或一份主食 → 接受或拒绝 → 查看具体做法。

当前仓库是数据工程与应用开发交接起点。已有材料和参考实现不代表微信小程序、线上接口或生产内容审核已经完成。先阅读 `README.md`、`docs/PRD.md`、`docs/ARCHITECTURE.md`、`docs/API.md`、`docs/AGENT_TASKS.md`、`docs/ACCEPTANCE.md`，再执行任务。数据字段以仓库 Schema 和已验证代码为准，文档发生冲突时先修正契约并记录决定，不能在客户端另造一套字段。

## 开始工作

1. 按 README 执行离线构建、校验和测试，记录真实退出状态。先复现当前基线，不重新调查数据源。
2. 阅读源版本锁、种子审核记录和质量报告，区分原始内容、自动抽取、agent 核对、人工审核、实烹记录。
3. 从 `docs/AGENT_TASKS.md` 领取一个有明确输入输出的任务，说明依赖和本次可验证的完成条件。
4. 优先复用已有导入器、校验器、参考推荐逻辑和契约；只有出现明确需求时才替换，并用等价场景验证。
5. 完成后报告修改、验证命令、实际结果、尚未完成的依赖。没有 AppID、开发者工具或真机记录时，不写“小程序验收通过”。

当前参考推荐只实现口味、菜系、口感、优先食材与尝新相关排序，没有低精力分值。精力入口须补主动操作和负担数据、契约与测试后开放。样板没有 verified 总耗时和 verified 人数数据，严格时间/人数返回空结果属于当前预期，不能为了演示填值。`contracts/openapi.json` 是待开发接口说明，不是已经运行的服务。

## 数据与内容约束

- `data/raw/` 保存上游原始 bytes，不就地改写，不把自动润色后的文本冒充原文。
- 不直接修改生成数据。修改解析器、字典或 overlay 后重新构建。生成结果必须能追溯到输入及构建版本。
- HowToCook 固定到明确 commit；每份文件核验内容哈希。显式升级源版本时先生成差异，不能静默覆盖已有审核结果。
- 菜品与做法版本分开。菜名相同不证明做法相同；多来源、压力锅与普通锅版本均需明确关联。
- 食材从原料、计算和步骤交叉核对。保留原文和数量文本；可选材料、必需材料、替代组分别表达。
- 生米与熟米饭、干货与鲜货保留状态差异。别名不做过宽的模糊匹配。油盐和调料不能默认家家都有。
- 复合调料成分未知时不能得出“不含某成分”的结论。菜系、目录名、食材词命中都不能代替完整审核。
- 时间包含必要备菜和前置条件。总耗时、主动操作和等待时间分别表达；步骤可能并行，不能机械求和。源文估计不等于实烹结论。
- 不编造口味、菜系、营养、费用、器具、时间、来源许可或审核状态。未知保留 null/明确状态，不用 0、false 或空集合表示“已确认没有”。
- 原文中的“排毒”“抗衰老”等功效词只作为原始内容保存，不转成推荐标签或卡片宣传语。展示的选项必须有对应数据能力与覆盖说明。
- `agent_checked` 表示 agent 对照来源，不能改名为人工审核。30 条样板用于开发预览；发布资格按具体字段和用途审核。
- 不擅自为项目代码选择开源许可。上游许可按第三方声明保留，图片与外链独立判断；未经核实不下载和公开分发媒体。

## 推荐与反馈约束

- 先检查发布资格和硬条件，再按软偏好排序，最后随机抽取。随机化不能让不合格项重新入选。
- 默认生产路径不读取开发种子。开发预览权限由服务端/运行环境控制，不能接受客户端任意提升数据资格。
- 忌口、必需器具、严格时间、严格食材条件不得被打分、随机或空结果降级绕过。
- 严格条件所需字段未知时，按不满足处理；解释原因并允许用户明确调整可以放宽的条件。
- 库存只有食材 ID 时只能说明种类匹配，不能说明数量足够。严格数量模式必须具有可比较的数量、单位和份数。
- 同一轮按菜品去重，同菜不同版本不用于凑“换一道”。允许在候选用尽后由用户明确开启新一轮。
- 接受、收藏、做过、最近吃过分开记录。一次拒绝不推导永久讨厌；长期排除须来自用户明确设置。
- 反馈事件幂等，重试不得重复累计。相同事件 ID 对应不同正文时返回冲突；事件必须属于当前用户和会话。
- 测试允许注入固定随机种子；生产随机由服务端控制。不要通过固定第一项伪装为随机，也不要让客户端修改发布和硬筛选规则。

## 工程边界

- 数据源 adapter 只处理来源差异；领域推荐逻辑不得依赖 HowToCook 路径、Markdown 标题或供应商字段。
- repository 隔离 JSON、SQLite 与未来线上数据库；客户端通过应用接口获取数据，不访问上游 GitHub 或数据库文件。
- Schema、API、枚举、事件和错误码保持一致。破坏性字段变更需要版本升级、迁移和回滚说明。
- 本轮不引入复杂机器学习、向量数据库、微服务或实时库存系统来替代可解释的首版规则。
- 不提交密钥、个人数据、临时凭证和真实 AppSecret。账号与第三方付费依赖只写配置说明，不伪造可用凭证。
- 测试聚焦实际风险：漏料、未知值、时间前置、器具 AND/OR、权限、并发去重、幂等和版本更新。不为了数字堆积重复测试。

## 交付要求

每个任务交付可运行代码、相应契约或文档变更、最小必要的验证结果。注明哪些结果来自真实 HowToCook 数据、哪些来自合成边界样例。未运行的检查写“未运行”，外部环境尚未验证写“待验证”。
