# 今日何食首版产品需求

版本：0.1；目标平台：微信小程序；当前内容源：HowToCook 固定版本。

## 1. 产品目标与边界

帮助用户根据当下时间、精力、食材和偏好，接受一个今天可执行的菜谱，并查看与推荐条件一致的完整做法。

首版支持一道菜或一份主食，明确是否需要配饭。主要场景为 1—2 人日常居家做饭。多人多菜自动配餐、外卖、餐馆、实时价格、精确营养和疾病饮食指导不在 P0。条件为空时允许开始推荐；严格条件不满足时允许诚实地返回空结果。

当前交付是数据与开发基础。真实源内容、开发样板和合成测试数据分别保存。源文可以阅读，不代表时间、器具或饮食限制已获得发布资格。

### 当前能力与目标需求的区别

本文件的 FR 编号描述待开发的首版目标，不代表页面或 HTTP 服务已经存在。当前可运行入口是 Python CLI 和纯规则参考。

| 能力 | 当前状态 | 开发要求 |
| --- | --- | --- |
| 口味、菜系、口感、优先食材、尝新排序 | 参考逻辑支持，具体能否命中取决于已标注内容与上下文 | 应用层复用或通过等价测试移植 |
| 精力/省事排序 | **尚未实现**；没有低精力分值 | 补充主动操作及负担字段、标签和测试后开放入口 |
| 严格总时间 | 契约已有 `max_total_minutes`，样板没有 verified 总时间 | 当前严格请求应空结果，不能把 source_estimate 当验证值 |
| 严格人数 | 契约已有 `servings`，样板没有 verified 人数范围 | 当前严格请求应空结果，后续确认份数及缩放规则 |
| 线上会话、反馈、收藏、设置与微信页面 | **尚未实现** | 按任务书开发，OpenAPI 仅作为待完善契约 |
| 生产内容集合 | 当前没有已发布菜谱 | 默认 production 返回 `no_candidate` 为正常行为 |

## 2. 首版用户流程

进入首页并查看已保存设置 → 选择或跳过本轮条件 → 发起推荐 → 查看一张卡片 → 接受、收藏或换一道 → 接受后查看材料及步骤 → 用户主动记录“做过”。

P0 页面包括首页/条件、推荐卡、菜谱详情、收藏、常用设置。内容审核界面可先用管理工具实现，业务权限与用户界面分开。

## 3. 输入需求

| 编号 | 要求 | 默认与边界 |
| --- | --- | --- |
| FR-01 | 首页优先询问多久开饭、愿意花多少精力、想用掉什么食材 | 三项均可跳过，更多偏好折叠展示 |
| FR-02 | 更多偏好支持口味、菜系、餐食形态和人数 | 菜系/口味默认影响排序；用户选择“必须/只看”才成为硬条件 |
| FR-03 | 食材模式区分优先使用、只用已确认食材种类、允许采购 | “想用掉番茄”不意味着禁止采购其他材料 |
| FR-04 | 保存常用器具、已确认常备食材、明确排除食材 | 用户可改、可清空；未知状态不得自动补全 |
| FR-05 | 区分本轮条件和长期设置 | 本轮选择不未经确认写入长期设置；新一轮可复用或重置 |

时间选项建议为 15/30/60 分钟和不限。**当前 `max_total_minutes` 表达严格上限，尚无“尽量在某时间内”的软偏好字段**；如增加后者，先扩展契约和排序规则。没有经过确认的总时间，不能进入严格时间候选池。精力值建议为省事、正常、愿意认真做，目标是按主动操作与负担排序；该能力当前尚未实现，不开放可操作的精力入口，也不虚构精力匹配理由。

选项可用性来自当前发布集合的覆盖统计。没有对应审核数据的入口应标为尚未支持或暂不开放，不能为了让界面显得完整而承诺所有筛选能力。来源中的“排毒”“抗衰老”等功效描述不进入推荐标签与卡片文案。

P0 食材库存可以只记录种类，但卡片需明确“种类匹配，数量请按菜谱确认”。未来严格用量检查需要数量、单位、份数及换算规则；在此之前不显示“库存足够”。

## 4. 推荐卡与详情

| 编号 | 要求 | 验收方向 |
| --- | --- | --- |
| FR-06 | 每次展示一个具体做法版本 | 卡片、详情、反馈记录引用同一版本；不能进入详情后换成另一做法 |
| FR-07 | 展示菜名、图片或中性占位、份量、餐食形态、食材和器具提示 | 未审核图片不展示；一道下饭菜明确提示是否需要配主食 |
| FR-08 | 时间显示说明口径和前置条件 | 源文估计明确标注；未知不显示 0 分钟；需现煮饭/提前浸泡必须可见 |
| FR-09 | 显示 2—3 条有数据支持的匹配理由，允许更少 | 未命中的条件不写成推荐理由；无证据时不凑满三条 |
| FR-10 | 接受后打开完整材料、用量文本和分步做法 | 保留来源链接和必要归属；步骤中的可选分支保持清楚 |

卡片按钮为“就做这个”“换一道”“收藏”。“就做这个”记录接受并打开详情，不自动记录做过。详情显示原文中的数量公式或范围，不能未经支持直接把所有材料线性乘以人数。超出支持的份量范围时提示核对。当前源文人数/用量可以作为来源信息展示，但尚不支持可靠的人数硬筛选。

客户端不得直接运行未经清理的 Markdown/HTML、自动播放外链媒体或执行菜谱中的命令片段。正文按受限的文字、列表、链接和图片组件渲染；链接目标按服务端输出规则处理。

## 5. 拒绝、历史和反馈

| 编号 | 用户行为 | 预期影响 |
| --- | --- | --- |
| FR-11a | 换一道但不提供原因 | 记录曝光/跳过，继续本轮去重，不推导长期偏好 |
| FR-11b | 今天不想吃 | 只调整本轮或当天排序，保存明确作用域 |
| FR-11c | 太麻烦 | 下次推荐优先更低操作负担；不能自动推断某食材不喜欢 |
| FR-11d | 食材不方便 | 允许修正库存/采购条件；不擅自修改用户库存 |
| FR-11e | 最近吃过 | 记录近期状态，降低近期重复 |
| FR-11f | 一直不吃某种食材 | 用户确认后更新长期排除，可撤销 |
| FR-12 | 收藏、取消收藏、确认做过 | 独立事件；重试不重复累计；收藏不是做过 |

同一轮按菜品身份去重，而非只按做法版本去重。菜品候选用尽后给出“本轮已看完”和“开启新一轮”入口，不悄悄重复。接受后取消查看不增加做过次数。近期去重以用户明确做过/最近吃过为依据，曝光另用于本轮去重。

## 6. 空结果与异常状态

| 状态 | 页面行为 |
| --- | --- |
| 正在请求 | 显示加载状态；禁止同一次操作产生重复并发点击 |
| 首次无候选 | 说明受限条件与数据覆盖不足，展示可选择的单项放宽建议 |
| 本轮候选用尽 | 保留当前条件，允许用户明确开启新一轮 |
| 无对应审核数据 | 说明“暂无经过相应条件审核的菜谱”，不能说世界上不存在这种菜 |
| 网络失败 | 提供重试；保留条件和当前卡片；重试使用同一幂等标识 |
| 详情版本已下架 | 说明版本不可用，停止推荐，保留已发生的历史事件 |
| 数据解析/契约错误 | 返回可定位的错误和请求标识；不将未知字段转换成默认通过 |

FR-13：放宽时间、采购或菜系必须经用户明确选择。明确排除项和必需器具不自动解除。多个限制共同造成空结果时，只报告实际检查得到的原因；不把每一个单独放宽项都承诺为一定有结果。

## 7. 内容运营与发布

FR-14：管理工具支持来源查看、材料/标签修改、审核状态、版本发布、下架、按条件检查候选覆盖。原文与标准化数据并排显示。人工修改保存在 overlay 或审核版本中，生成器重跑不得覆盖。

资格按用途区分：正文可读、可按食材筛选、可按器具筛选、可按严格时间筛选、可按明确排除条件筛选。正文审核不隐含全部标签已审核。当前 agent_checked 种子只进入开发预览，生产 published 条目需完成对应发布检查。

## 8. 非功能与隐私

- 首屏不要求手机号、精确位置或健康信息。匿名使用与后续账号同步分别设计。
- 收藏和偏好支持删除；跨设备合并需有明确的账号边界，不按设备全局共享。
- 用户输入不发送给 HowToCook；内容在数据流程导入，线上推荐读取本地应用数据。
- 不把完整用户请求或偏好写入公开日志；运维日志使用必要标识和错误信息。
- 幂等反馈、用户所属校验、会话版本与限流由服务端保证。客户端检查用于体验，不能替代服务端校验。
- 性能目标需在指定测试环境中设定并实测。当前不声称已满足线上并发或小程序包体限制。

## 9. 观察指标与首版完成条件

记录发起推荐、展示、跳过、接受、收藏、做过和空结果事件。决策完成率 = 至少接受一次的推荐会话数 / 发起推荐的会话数；同时看首次接受前卡片数、决策时间、空结果率和做过后的反馈。接受率不代替实际做过率。

P0 完成需要：约定支持场景的数据覆盖达到目标、核心验收通过、开发者工具与真机记录完成、生产发布门槛可执行。建议覆盖目标为 80 个预定义受支持场景中至少 90% 各有 5 个可用菜品；这是后续试验目标，当前未达成，也不意味着应强行扩大所有筛选组合。
