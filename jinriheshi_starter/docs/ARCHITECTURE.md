# 可扩展的数据与应用架构

## 1. 设计决定

使用 HowToCook 作为第一个内容来源，保留不可变原文与来源版本；业务读取统一数据模型。当前 Python 数据工具负责离线导入、构建、验证和本地演示。后续微信小程序建议使用原生 TypeScript，应用后端通过独立接口提供推荐和反馈。

先保留清晰的模块边界，再按实际需求选择线上数据库与部署方式。JSON 适合审阅、版本控制和交换；SQLite 用于本地应用镜像与集成验证；未来 PostgreSQL 或云数据库通过 repository 接入。不要让小程序依赖 JSON 文件路径、SQLite 表细节或上游 Markdown。

当前边界文件为 `schemas/recipe.schema.json`、`schemas/recommendation_request.schema.json`、`schemas/recommendation_response.schema.json`、`schemas/event.schema.json`。`contracts/openapi.json` 描述待开发 HTTP 接口，已定义 Options、PublicRecipe、会话 revision 和永久排除目标。具体请求与状态见 `API.md`；契约存在不代表服务已实现。

## 2. 模块职责

| 模块 | 输入和输出 | 不应承担的职责 |
| --- | --- | --- |
| Source adapter | 固定源版本、文件清单、原文 → 来源记录及抽取候选 | 不决定用户偏好，不自动通过人工审核 |
| Canonical builder | 来源候选、字典、overlay → 统一 RecipeVersion 数据 | 不直接修改 raw，不把缺失字段补成猜测值 |
| Validator | Schema、字段引用、证据、哈希、资格 → 失败原因及质量报告 | 不为了校验通过静默改值 |
| Recipe repository | 统一查询、按版本读取、发布状态 → 领域对象 | 不包含随机、推荐打分或界面文案逻辑 |
| Recommendation domain | 条件、候选、历史 → 资格判断、排序、随机选择、理由 | 不识别供应商字段，不直接调用微信 SDK |
| Application service | 用户、会话、事件 → 授权、幂等、持久化、事务和接口响应 | 不信任客户端传来的发布资格或用户身份 |
| Mini program | 条件输入、卡片、做法、反馈 → 接口请求与显示 | 不自建第二套推荐规则，不直接访问原始数据源 |

推荐参考实现用于验证规则与数据契约。若后端改用 TypeScript，需要把相同场景作为契约测试，确保硬筛选、去重、未知值语义一致，不能只凭返回菜名相同判断等价。

## 3. 内容对象与身份

- 菜品 Dish 聚合同一道菜的不同做法，用于本轮去重与历史。
- 做法版本 RecipeVersion 绑定步骤、材料、器具、份量、时间和审核状态。步骤或执行条件发生实质变更需产生新版本。
- 来源 SourceRecord 记录来源 ID、路径、commit、内容哈希和许可。源路径不是跨来源业务主键。
- 食材 Ingredient 使用稳定 ID 与别名，保留状态。配料需求关联角色、必需性、数量文本、替代组和证据。
- 证据记录字段来源和检查方式。来源估计、规则抽取、agent 核对、人工确认、实烹记录要能区分。
- 反馈 Event 绑定用户、会话、菜品、做法版本、事件类型、作用域和客户端幂等键。

当前单来源可由稳定算法为源路径生成初始标识。新增来源或路径重命名时，通过显式映射保留业务身份，不能重新生成后让收藏失效。相同菜名只生成待核对的重复候选，不自动合并。

## 4. 数据分层与更新

1. `data/raw/` 保存来源原文和上游许可，不手工改写。
2. 源锁和文件 manifest 固定 commit 与哈希，下载失败不能写出完整成功状态。
3. 字典保存食材/器具稳定 ID、别名和必要状态。
4. overlay 保存针对指定原文哈希的补充与核对结果。
5. 构建产物保存全量 draft 与开发种子，并生成质量报告。
6. 生产发布集合由发布检查生成；开发预览状态不得自动晋升为 published。

上游更新时按新增、修改、删除分类。原文 SHA 改变的 overlay 标记待复核，不能直接应用于新文。删除或许可变化需影响发布资格，但历史事件继续保留版本引用。一次发布包含数据版本和构建版本，支持切回上一份完整产物；不做半批次切换。

相同锁、字典、overlay 和工具版本构建应产生相同业务内容。若报告需要运行时间，把运行元信息与业务内容哈希分开，避免每次重建导致全部条目变更。

当前生成路径为 `data/generated/recipes.jsonl`（全量统一记录）、`seed_recipes.jsonl`（开发样板）、`catalog.json`（目录）和 `build_report.json`（数量、资格及哈希）。SQLite 镜像由显式导出命令生成；不把镜像当手工维护的唯一源。

## 5. 条件表达

硬条件与偏好在请求中分开，服务端校验二者的作用域。服务器合并本轮请求和已确认长期设置，并保存本轮条件快照。用户修改本轮条件后创建新的条件版本，避免旧卡片反馈应用到错误条件。

器具同时支持 AND 与 OR：刀、砧板以及炒锅/平底锅二选一。替代器具只有在同一执行版本可行时才放入 OR；步骤或时间不同则创建不同版本。

食材替代组表达一组选一或更高约束。数量文本无法解析时保留原文，不能视为 0。P0 的库存种类匹配与未来严格数量匹配使用不同能力标志。

严格时间需要总时间上界、适用份数、前置条件及审核资格。仅有源文“约 15 分钟”不自动通过严格 15 分钟筛选；可以在开发预览中展示为来源估计。

当前样板的 `time.total_minutes`、`time.active_minutes` 未填 verified 结果，人数也没有 verified 资格。参考逻辑没有精力/负担打分；当前软偏好只有 tastes、cuisines、textures、priority_ingredients、novelty。未来增加精力时先定义字段与证据，不在前端借用难度星级伪装该能力。

## 6. 推荐与会话

先检查发布/预览权限与具体字段资格，再执行硬筛选。合格候选按软偏好评分；在高匹配集合中随机抽取，并对同菜多版本聚合去重。理由必须对应实际参与判断的字段。

会话维护条件版本、已展示菜品集合及当前序号。并发“下一道”应通过事务、乐观锁或等价机制处理，不能在两个请求中展示同一道菜而遗漏曝光。公共 API 不开放绕过审核的参数。测试代码可以注入可重复的随机源，生产使用服务端随机。

空结果应区分没有合格数据、本轮已看完、条件过窄和服务失败。可放宽建议通过真实重算或保守说明生成，不保证每个单项调整都能产生结果。明确排除项不自动放宽。

## 7. 事件持久化

接受、收藏、取消收藏、做过和拒绝原因独立。使用用户/匿名主体与客户端事件 ID 的组合唯一键；同键同内容重试返回首次结果，同键不同内容返回冲突。事件必须引用当前主体可访问的会话和版本。

收藏可以维护当前状态，同时保留事件；做过是明确动作，不能从打开详情推断。事件写入与状态更新在同一事务中执行。服务端接收时间与客户端发生时间分开，时间异常不覆盖服务端顺序。

## 8. 契约与版本迁移

JSON Schema 是文件边界；API 契约是客户端边界。未知枚举默认失败或按明确兼容规则处理，不静默映射为“无偏好”。不兼容变更升级 schema/API 版本，并提供旧数据迁移、兼容窗口和回滚路径。

CLI 推荐请求含 `schema_version` 和可注入的 `context`，CLI 另接受 `--mode` 与测试用 `--seed`。公开创建会话只接受 constraints/preferences；context 由服务端根据主体与历史构造，生产 mode 固定由部署配置决定，随机源不来自客户端。不能直接将 CLI 参数做成公共 API 入参。

字典 ID 一旦发布保持稳定。删除别名可以修正匹配，删除 ID 需要 tombstone 或迁移映射；业务记录不能引用悬空食材、器具或菜品。API 不直接暴露完整原始内容、内部审核备注或供应商凭证。

## 9. 后续扩展

| 扩展 | 预留方式 | 触发时再实现 |
| --- | --- | --- |
| 第二个菜谱来源 | 新 adapter 与来源登记；统一模型不变 | 来源身份映射、字段冲突和版本策略 |
| 多种做法/器具 | 同 Dish 多 RecipeVersion | 版本选择、等价关系和场景覆盖 |
| 多人多菜配餐 | 组合层使用多个已合格版本 | 重复食材、并行时间、总用量和偏好交集 |
| 价格与营养 | 独立计算结果，保存来源、地区/日期、份量口径 | 成分映射、单位换算与误差处理 |
| 账号与跨设备 | 领域主体与微信身份映射分离 | 登录、匿名合并、数据删除和同步冲突 |
| 个性化推荐 | 保留明确事件与作用域 | 有足够反馈后评估，继续保留硬筛选边界 |

## 10. 部署与验证边界

数据工具离线可运行与小程序上线是不同验收项。线上部署需要确定数据库、服务域名、鉴权方式和内容发布集合。微信 AppID、开发者工具预览、合法域名、真机网络与包体检查属于后续真实环境验证，不能由本地 Python 测试替代。
