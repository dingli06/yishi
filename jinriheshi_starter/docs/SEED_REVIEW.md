# 30 条 HowToCook 开发样板与待审核事项

## 1. 这批数据可以用于什么

本批是固定上游版本的开发标注样板，用于检验导入、同义词归一、筛选、详情展示和审核流程。标注由开发代理对照原文完成，**没有经过真人厨房审核或实烹计时，不是已发布菜谱库**。

- 上游：`Anduin2017/HowToCook`。
- 固定 revision：`0e106eea348c734fe1586f781202994439cf98a5`。
- 原文：`data/raw/howtocook/<revision>/dishes/...`，按 revision 隔离保存。
- 标注：`data/overlays/howtocook_seed.json`，30 条，341 个配料关联。
- 食材词典：`data/dictionaries/ingredients.json`，115 项。其中鲜香菇是用于鲜干区分的预留词条，当前样板只使用干香菇。
- 器具词典：`data/dictionaries/equipment.json`，28 项。
- 初步对照状态：18 条 `review.status=agent_checked`，12 条 `needs_review`。这些状态都不等于生产发布批准。
- 所有记录：`review.cooking_tested=false`；`time.total_minutes=null`；`time.active_minutes=null`。
- 3 条的器具状态为 `agent_checked`，仅表示源文中明示的必要器具经代理核对，其余25条明确待审；发布仍需独立审核器具完整性、器具容量和可替换关系。

## 2. 标注范围和证据规则

每条都读取原料、计算、操作和附加内容。对明确出现的配料保留原文证据，并补入只在计算或步骤里出现的材料。每项证据的 `quote` 必须是对应原始 Markdown 的精确子串；`source_sha256` 对原始 UTF-8 文件 bytes 计算，不能对格式化后的正文计算。

`agent_checked` 的含义是“代理已完成这次源文对照”，不是“完全可信”，也不是“真人已验证”。已识别的问题继续写在 `review.issues`，例如数量口径冲突、原文用量待核、工具推断和分支做法混杂。不能因为该字段为 `agent_checked` 就清空问题或自动发布。

### 配料规则

- `required`：当前原文主体做法需要。
- `optional`：原文明示可选、可省，或附加口味分支；保留相关来源证据。
- `alternative`：原文明示的二选一，使用 `alternative_group` 表达。组内任选一种，不能要求同时拥有两种，也不能把整组当成非必需。
- `unknown`：名称、必需性或版本归属仍有冲突。该记录不能获得严格“材料齐全”资格。
- 主料/调料/其他材料由 `role` 单独表达。调料仍可能是必需材料，水也不自动假设用户已确认。
- `quantity_text` 保留原文用量行，可能含公式、区间、单位或多个替代选项。未完成机器可计算的数量解析；`null` 表示没有可靠归一到当前材料的用量文本。步骤里另有数量时，仍能从 `evidence` 查到，不能把 `null` 当零。
- 未注明的任意熟肉、其他蔬菜等开放式变体，会阻止完整性通过，后续需要固定成独立做法版本。

### 标签规则

口味、口感和菜系使用源文感官描述中的精确证据，`tag_evidence.value` 指向具体标签 ID。仅仅属于 `vegetable_dish` 目录，不会产生严格素食标签；仅仅叫“麻婆豆腐”，不会推断其配料或辣度。不存在“未知菜系等于家常菜系”的默认填充。

`meal_form` 和 `standalone_meal` 是代理给出的产品分类候选，需要真人编辑确认。独立成餐仅指本产品的一餐形态，不是营养均衡声明。电饭煲白米饭、茶叶蛋、单个太阳蛋没有被标为完整的一碗饭菜。

原文中的“养心安神”“增强免疫力”等功效描述没有被转成推荐标签。源文热量也没有写入可用于精确筛选的营养字段。

### 时间和器具规则

`source_estimate_minutes` 只转写介绍段中的时间表达，便于来源对照；它可能只是炒煮或加热时间，不是已审核的完整开饭时间。不能用它满足严格15分钟、30分钟等条件。

`required_all` 表示同时必需，`required_any` 中每个数组表示该组至少选一项。器具清单不表达数量、容量和条件性工具；这些缺口已列入审核任务。源文没有说炒锅时，不添加“默认炒锅”。具体版本的器具替换不得由名称相近自动推断。

## 4. 词典扩展约定

ID 是稳定主键；名称修改不应重建 ID。新来源先通过别名匹配到既有 ID，无法确定的词进入待审，不用模糊相似度直接合并。

- 西红柿/番茄共用 `ing_tomato`。
- 生米为 `ing_raw_rice`，熟米饭为 `ing_cooked_rice`。
- 干香菇为 `ing_dried_shiitake`，鲜香菇为 `ing_fresh_shiitake`。
- 泛称葱、小葱、大葱、洋葱、白洋葱保留不同ID；匹配需要优先最长词，不能把“洋葱”子串当作“葱”。
- 白芝麻和明确熟制的白芝麻分别保存。
- 酱油、生抽、老抽不互设为同义词；料酒/黄酒也不合并。
- 复合调料、加工肉、未明确成分的食用油等使用 `component_status=unknown`。空 `components` 不等于不含某成分，不能用来做过敏或严格饮食安全保证。

词典中的 `state=unspecified` 表示来源没有给出足够状态信息。例如银耳不能因通常需要泡发就直接补成干品。未来扩展冷冻、预熟、带骨等状态时，应先更新数据契约与迁移规则。

## 5. 发布前需要完成的任务

1. 将混合做法拆为可执行版本；明确默认可选项、替代组以及对应步骤。
2. 由内容编辑逐项确认原料完整性，解决 `unknown` 和 `review.issues` 中的冲突。
3. 用实际器具、份量和食材状态核对时间；只更新对应版本，不回填所有同名菜。
4. 审核器具完整性、数量、容量和可替换组合，并在改动步骤时重新审核。
5. 图片逐项核对许可。本批只提供原始正文和标注，不自动下载或发布源文图片。
6. 由独立发布流程写入生产发布状态；禁止导入脚本、模型标注或开发预览自动完成发布。

上游 revision 或内容 SHA256 变化时，旧标注必须标为过期待审。新原文不能继续沿用旧版本的审核结论；保留旧版本供已接受菜谱和反馈追溯。
